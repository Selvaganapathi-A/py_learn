# Digest authentication with SHA-256
<!--  -->
Let’s break down **Digest Authentication with SHA-256**, step-by-step, in full technical detail. It's more secure than Basic Auth, but less used today due to the rise of HTTPS, JWT, OAuth2, etc. However, it still holds ground in **embedded devices**, **legacy systems**, and **low-bandwidth environments**.

---

## 🔐 What Is Digest Authentication?

Digest Auth is an HTTP authentication scheme where the **client proves knowledge of a password** without sending it in plaintext.

> It uses a **challenge-response handshake**, hashing credentials using an agreed algorithm (like **SHA-256** instead of MD5).

Digest Auth:

* Avoids sending passwords directly.
* Protects against replay attacks (via nonce).
* Does **not require HTTPS**, though it’s still highly recommended.

---

## 🧰 Digest Auth Flow (SHA-256 variant)

We'll use the following headers and terminology:

* `username`
* `realm`: A string that identifies the protected area (e.g., "Restricted Area")
* `nonce`: A server-generated random token (changes often)
* `uri`: The URI being accessed
* `cnonce`: A client-generated nonce
* `response`: The final hashed string client sends
* `qop`: Quality of Protection, usually `auth` or `auth-int`
* `algorithm`: `SHA-256`

---

### 📍 Step-by-Step: Digest Auth with SHA-256

---

### 🔁 1. Initial Request (No Auth Header)

```http
GET /secure-data HTTP/1.1
Host: api.example.com
```

---

### 🔐 2. Server Responds with 401 Challenge

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Digest realm="MyRealm",
  nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
  opaque="5ccc069c403ebaf9f0171e9517f40e41",
  qop="auth",
  algorithm=SHA-256
```

#### Server-Side

* Chooses realm + nonce + optional opaque string.
* Specifies `algorithm=SHA-256`.

---

### 🔐 3. Client Sends Authenticated Request

Client now computes:

#### 🧠 Hash Computations

##### A1 (User credentials hash)

```
A1 = SHA-256(username:realm:password)
```

##### A2 (Method + URI)

```
A2 = SHA-256(method:uri)
```

##### Final Response Hash

```
response = SHA-256(
  A1:nonce:nc:cnonce:qop:A2
)
```

#### Headers Sent

```http
GET /secure-data HTTP/1.1
Host: api.example.com
Authorization: Digest username="element",
  realm="MyRealm",
  nonce="dcd98b7102dd2f0e8b11d0f600bfb0c093",
  uri="/secure-data",
  qop=auth,
  nc=00000001,
  cnonce="0a4f113b",
  response="6629fae49393a05397450978507c4ef1",
  algorithm=SHA-256
```

> ⚠️ `nc` is nonce count; it increases with each use of the nonce.
> ⚠️ `cnonce` is a random string generated by the client to prevent replay attacks.

---

### ✅ 4. Server Verifies and Responds

#### Server-Side

* Reconstructs A1 using the stored password hash.
* Calculates A2 and the expected response hash.
* Compares with client-provided `response`.
* If matches:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "data": "protected content" }
```

* If not:

```http
HTTP/1.1 401 Unauthorized
```

---

## 🔄 Flow Summary Table

| Step | Client                                   | Server                    |
| ---- | ---------------------------------------- | ------------------------- |
| 1    | Sends request without auth               | Responds with 401 & nonce |
| 2    | Computes hashes and builds Digest header | Validates response hash   |
| 3    | Sends request with Digest header         | Sends 200 OK or 401       |

## 📌 Why SHA-256 Instead of MD5?

### 🔥 Advantages

* MD5 is deprecated due to collisions.
* SHA-256 offers better integrity and security.

### 🔄 Compatibility

* Digest Auth with SHA-256 isn’t supported everywhere.
* Requires explicit implementation on **both client and server**.

---

## 🧪 Example Hash Computation (Python-style Pseudocode)

```python
import hashlib

def sha256(data: str):
    return hashlib.sha256(data.encode()).hexdigest()

username = "element"
realm = "MyRealm"
password = "secret"

method = "GET"
uri = "/secure-data"
nonce = "dcd98b7102dd2f0e8b11d0f600bfb0c093"
cnonce = "0a4f113b"
nc = "00000001"
qop = "auth"

A1 = sha256(f"{username}:{realm}:{password}")
A2 = sha256(f"{method}:{uri}")
response = sha256(f"{A1}:{nonce}:{nc}:{cnonce}:{qop}:{A2}")
```

---

## 🔐 Server Implementation Notes

* You must **store passwords hashed with SHA-256**, not plaintext.
* Server must **track nonces** and possibly enforce timeouts.
* Validate `nc` (nonce count) and `cnonce` to prevent replay attacks.

## 🔐 Digest Auth (SHA-256) vs Alternatives

| Feature           | Digest Auth (SHA-256) | Basic Auth | API Key | OAuth2 |
| ----------------- | --------------------- | ---------- | ------- | ------ |
| Secure over HTTP? | ⚠️ Partially          | ❌          | ❌       | ❌      |
| Sends password?   | ❌ No                  | ✅ Yes      | ❌       | ❌      |
| Stateless?        | ✅                     | ✅          | ✅       | ✅ / ❌  |
| Replay protection | ✅ via nonce           | ❌          | ❌       | ✅      |
| Common support    | ❌ (rare)              | ✅          | ✅       | ✅      |

---

## 🧩 When to Use Digest Auth (SHA-256)?

✅ Pros:

* Simple challenge-response without revealing password
* No need for TLS (but recommended)
* Stateless
* Low overhead (no cookies or tokens)

❌ Cons:

* Limited adoption in modern clients/libraries
* Complex for browser support
* Not flexible like OAuth2 or JWT
* Needs custom implementation for SHA-256 (most use MD5 by default)

---

## ✅ Summary

Digest Auth with SHA-256 is:

* A **challenge-response** protocol
* More secure than Basic Auth
* Suitable for systems where HTTPS isn’t always available (embedded, IoT)
* Not ideal for SPAs, mobile apps, or modern web apps
* **Obsolete** for most internet-facing services (replaced by OAuth2, JWT, etc.)
